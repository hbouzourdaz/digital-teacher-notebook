# المعمارية — Architecture

## المبدأ

فصل صارم بين أربع طبقات. لا SQL في مكوّنات React، ولا منطق أعمال في الـ IPC، ولا وصول مباشر لقاعدة البيانات من الواجهة.

```
renderer (React + Zustand)
        │  window.api.<namespace>.<method>()   ← واجهة بيضاء مُنشأة من عقد واحد
        ▼
preload (contextBridge)                     ← لا يكشف fs ولا sqlite ولا child_process
        ▼
IPC layer (src/main/ipc)                    ← قناة واحدة لكل عملية + تحقق Zod + رسائل عربية
        ▼
services (منطق الأعمال)                     ← التنقيط، لوحة التحكم، البحث، التصدير، البيانات التجريبية
        ▼
repositories (وصول البيانات)                ← Prepared Statements فقط، بلا SQL خام من الخارج
        ▼
SQLite (better-sqlite3)  →  userData/notebook.db
```

## لماذا طبقة IPC بمخططات Zod؟

كل قناة تُسجَّل عبر دالة مساعدة واحدة `handle(channel, schema, handler)`:

1. **تحقق** — يُحلَّل مدخل الواجهة بمخطط Zod قبل الوصول إلى أي منطق. أي حقل غير مصرّح به يُرفض.
2. **رسائل آمنة** — أخطاء SQLite الخام لا تصل للمستخدم؛ تُترجم إلى نص عربي مفهوم، والتفاصيل التقنية تُكتب في السجل
   المحلي فقط (`humanizeError`).
3. **عقد واحد للحقيقة** — شجرة القنوات في `src/shared/ipc.ts` تُشتق منها واجهة الـ renderer (`createApi`) وفي نفس
   الوقت تُستخدم في التسجيل، واختبار الوحدة يقارن الاثنين فلا يمكن أن تتباعدا.

## عقد القنوات

```ts
export const IPC = {
  students: { list: 'students:list', create: 'students:create', ... },
  schedule: { list: 'schedule:list', move: 'schedule:move', ... },
  ...
} as const
```

`createApi(invoke)` تبني كائن الـ API من نفس الشجرة، لذلك إضافة قناة جديدة تعني:
إضافة سطر في `IPC` + معالج في `registerIpc()` + سطر في واجهة `NotebookApi` (توثيق الأنواع).

## تدفّق البيانات في الواجهة

- **SQLite هو مصدر الحقيقة.** حالة Zustand (`store/app.ts`) مجرّد ذاكرة عرض للبيانات المرجعية
  (السنة الفعّالة، الأستاذ، المؤسسة، المواد، المستويات، الأقسام، المظهر).
- كل شاشة تجلب بياناتها عبر `useAsync(loader, deps, initial)` من الـ IPC، مع `reload()` لإعادة الجلب.
- التحديث موضعي: تغيير علامة في دفتر التنقيط يحدّث الخانة ويعيد حساب بطاقات الإحصاء فقط، لا الصفحة كاملة.
- `window.notebookEvents.onReload` تُستعمل بعد الاستعادة من نسخة احتياطية لإعادة التحميل الكامل.

## طبقة الطباعة (src/main/printing)

الطباعة وحدة مستقلة عن الواجهة، مبنية على ثلاث طبقات ملفّات تفصل المسؤوليات:

| الملف | الدور | قابلية الاختبار |
| --- | --- | --- |
| `documents.ts` | يبني متن كل وثيقة من قاعدة البيانات (11 وثيقة) + ورقة الغلاف + CSS الوثيقة | نعم: يُختبر بـ SQLite حقيقي |
| `paginate.ts` | منطق خالص: تقسيم المتن إلى وحدات، خطة الأوراق، الترقيم، اختيار الصفحات، قياس متدفق | نعم: دوال نقية بلا إلكترون |
| `render.ts` | القياس داخل نافذة إلكترون مخفية ثم تركيب أوراق A4 المرقّمة | تكاملي |
| `pdf.ts` | إرسال إلى الطابعة أو توليد PDF (`printToPDF`) بنافذة معزولة | تكاملي |

الفكرة المعمارية: **المعاينة والطابعة و PDF تستعمل نفس HTML**، فلا يمكن أن تختلف الورقة المطبوعة عن التي رآها الأستاذ.
منطق التوزيع والترقيم بلا أي اعتماد على إلكترون (مقاييس A4 بالمليمتر والبكسل)، ولذلك يُغطّي `tests/paginate.test.ts`
كل قواعد الأوراق، و`tests/print.test.ts` يتحقق من الغلاف والمحتوى وسلوك الأيام بنفس بيانات الوثيقة الحقيقية.

تفصيل الحلقة الكاملة (قياس ⇒ توزيع ⇒ ترقيم) في [`PRINTING.md`](./PRINTING.md).

## نظام التصميم

كل الأنماط مركّزة في `src/renderer/src/styles/index.css` و`tailwind.config.js`:

- **الرموز (tokens):** متغيرات CSS للسطوح والحدود والنصوص (`--surface`, `--border`, `--text`…) تتغيّر تلقائياً مع
  الوضع الليلي (`html.dark`)، فكل مكوّن يتبع الثيم دون تكرار.
- **الخطوط:** Tajawal للواجهة (`font-ui`) وAmiri للوثائق (`font-doc`) — ملفات `.ttf` محلية في `resources/fonts`.
- **المكوّنات:** أصناف جاهزة (`.card`, `.btn-*`, `.badge`, `.table-wrap`, `table.grid`, `.cell-input`, `.stat-card`,
  `.sidebar-link`, `.section-title`) تُبنى بـ `@apply` فتضمن شكلاً واحداً في 17 شاشة.
- **الألوان الدلالية:** `brand` (كحلي) للأساسي، و‌`success/warning/danger/info` للحالات؛ وبطاقات الإحصاء
  (`StatCard`) تختار لونها تلقائياً من دلالة العنوان ولا تحتاج ضبطاً يدوياً في كل شاشة.
- **RTL:** خصائص منطقية (`inset-inline-start`, `border-inline-start-width`, `text-end`, `start-*`) بدل يمين/يسار
  الصريح، حتى تبدو الشرائط والظلال في مكانها الصحيح.
- **الحركة:** انتقالات قصيرة + `animate-fade-in`، مع احترام `prefers-reduced-motion`.

ملاحظة مهمة: صنف `grid` في Tailwind (`display:grid`) يتقدّم على عرض الجدول الافتراضي؛ لذلك تثبّت
`table.grid { display: table }` في CSS وإلّا انهارت كل جداول التطبيق.

### شريط تمرير واحد فقط

طُبقت قاعدة واحدة على كل الشاشات: **الصفحة هي منطقة التمرير الوحيدة**، وما عداها لا يُنتج أشرطة متكررة:

- `main` في الهيكل: `overflow-y: auto` مع `overflow-x: hidden` — فلا شريط أفقي على مستوى التطبيق أبداً.
- `.table-wrap`: `overflow-x: auto; overflow-y: hidden` — الجداول العريضة تُمرَّر أفقياً داخل بطاقتها وحدها،
  ولا يُضاف شريط عمودي داخلي فوق شريط الصفحة.
- `.scroll-y`: منطقة تمرير عمودية مقصودة فقط (سجل الأخطاء، محاورة الحضور، معاينة الطباعة).
- الأشرطة المتبقية رقيقة ومخصّصة عالمياً (`::-webkit-scrollbar` بعرض 8 بكسل، مقبض نصف شفاف بإطار شفاف
  و`background-clip: content-box`، ومسار شفاف) + `scrollbar-width: thin` للمتصفحات الحديثة.
- معاينة الطباعة تُقاس بنسبة التصغير المناسبة لعرض اللوحة (`scale` محسوب من `ResizeObserver`) بدل عرض الورقة
  بعرضها الحقيقي — فلا شريط تمرير أفقي في المعاينة حتى مع الورقة الأفقية.

## الحزمة الأصلية `better-sqlite3`

الحزمة مُترجمة لواجهة ABI واحدة فقط: نسخة Node للاختبارات، ونسخة Electron للتطبيق والمثبّت. لذلك نُبقي
نسختين في مجلدين منفصلين:

| المجلد | الواجهة | من يستعمله |
| --- | --- | --- |
| `node_modules/better-sqlite3` | Electron | التطبيق (`npm run dev`) والتغليف (`npm run dist`) |
| `node_modules/.node-abi/better-sqlite3` | Node | `npm test` (نسخة مصغّرة: `package.json` + `lib` فقط) |

`scripts/sqlite-runtime.mjs` يجهّز النسخة المطلوبة عند الحاجة، ويتحقّق من بصمة الملف الأصلي
(`build/.runtime-target` + الحجم + تاريخ التعديل) حتى لا يعيد العملية في كل مرة. النتيجة: التطبيق والاختبارات
يعملان في وقت واحد بلا خطأ «resource busy or locked»، ودون أي إنترنت بعد أول تجهيز (نسخة مخزّنة مؤقتاً على الجهاز).

## الأداء

- الفهارس على الأعمدة الحارّة (`date`, `class_id`, `student_id`, `academic_year_id`).
- الاستعلامات مرقّمة (`LIMIT/OFFSET`) في القوائم الكبيرة، بينما يحمّل دفتر التنقيط القسم كاملاً لأنه جدول إدخال.
- WAL mode و`busy_timeout` و`synchronous = NORMAL` لكتابة سريعة وآمنة.
- الحفظ في دفتر التنقيط يحدث لكل عمود عند مغادرة الخانة (لا كتابة لكل ضغطة مفتاح).
- الواجهة لا تحمّل كل البيانات عند الإقلاع: الإقلاع يجلب البيانات المرجعية فقط.

## الأمان (ملخص)

`contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, `webSecurity: true`, CSP في `index.html`،
منع التنقّل خارج التطبيق وفتح الروابط الخارجية في المتصفح. التفصيل في [SECURITY.md](SECURITY.md).

## الأخطاء والسجل

- `logger.ts`: سجل محلي في `userData/logs/app.log` مع تدوير عند 2 ميغابايت، ولا إرسال لأي مكان.
- في وضع التطوير تظهر الاستثناءات في الطرفية؛ في الإنتاج تبقى في السجل فقط.
- إن تعذّر فتح قاعدة البيانات: رسالة واضحة، **لا حذف**، واقتراح استعادة نسخة احتياطية.
